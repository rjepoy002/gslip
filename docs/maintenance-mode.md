# Maintenance mode deployment and lifecycle

Maintenance management is available to authenticated administrators through the
System Maintenance link or `maintenance.php`. Enable starts a 60-second warning;
End maintenance cancels warnings and restores access. Reasons are optional and
limited to 80 characters. Re-enabling an already enabled event does not restart it.

## Database and deployment

No schema changes or migration are required when the existing `system_settings`
table is present. No database changes were applied to the configured application
database during development. Tests create and remove a uniquely named isolated
test database.

An administrator enabling/disabling maintenance writes only one existing-table
setting, `maintenance_event`, containing a JSON event ID, enabled flag, deadline,
ended timestamp and reason. The application performs this parameterized SQL:

```sql
INSERT INTO system_settings (setting_key, setting_value)
VALUES ('maintenance_event', ?)
ON DUPLICATE KEY UPDATE setting_value = VALUES(setting_value);
```

This is application runtime SQL, not a query to paste manually: the bound value
is generated by the administrator action. No initial setting row is needed;
absence means maintenance is off. Existing users, gas slips, notifications and
push subscriptions are not modified by maintenance settings. Normal login still
updates the existing session token/last-login fields as before.

Deploy new files and modified files together. Merge the two maintenance-hook
lines into the live `includes/config.php`; preserve live database credentials,
URLs and secrets. Do not overwrite live configuration with local configuration.
No push to GitHub is required or performed by this implementation.

## Expiration and session handling

Warnings are transient current-state polling, never durable notification rows or
gas-slip notifications. Offline users have nothing to replay after an event ends.
Every poll reads the single authoritative setting, without browser caching.
Every explicit or deadline logout submits its event ID and session CSRF token.
The server serializes logout checks and administrator updates with a database
named lock, and ignores ended/previous events. No browser timer independently
destroys a session. New activations get a cryptographically random event ID.

The shared database-connection guard blocks non-admin application requests from
the effective deadline, including direct workflow endpoints. Admin authorization
is checked against the current active database account/session token. Login checks
maintenance after password validation and before creating the new session.
Online pages sharing the sidebar poll every three seconds and log out on a
server-confirmed active event. Background/suspended tabs may poll later; server
access restrictions do not rely on their timers. A request already in progress
when maintenance starts is not forcibly interrupted or rolled back.

## Browser push

Maintenance-start push is deliberately not queued: the existing sender rejects
the reserved `maintenance` type. Online warnings work without browser notification
permission. Normal gas-slip push delivery is unchanged. The service worker also
validates any delayed legacy `maintenance` payload's `event_id` against current
state before displaying it. Missing/stale/unverifiable events are suppressed.
Clicks validate again and navigate to current maintenance status or the dashboard,
never a logout URL from the payload. Page polling closes stale maintenance browser
notifications where the Notifications API supports it. Delivery/removal of OS
notifications cannot be guaranteed, and an already installed older worker must
update before the new worker behavior takes effect.

## Centered maintenance notice

The former full-width warning is now a centered SweetAlert2 dialog with a
maintenance icon, large live countdown, optional reason, and Acknowledge and Log
Out button. Its backdrop is `rgba(0, 0, 0, 0.65)`; outside clicks, Escape and the
close button cannot dismiss it. The existing dashboard/sidebar remain behind the
dimmed backdrop. Admins never receive this forced-logout notice.

Polling reuses the dialog for the current event. Ending maintenance closes only
the maintenance-owned dialog, without logging out the user. Confirm callbacks
retain their original event ID, so a delayed old callback cannot target a later
event. Logout requests are deduplicated while in flight. The visible countdown
uses the last server deadline sample; reaching zero requests fresh server state
before automatic logout. The server still validates every event/logout decision.
Successful acknowledgment and automatic logout now redirect to `maintenance.php`.
The maintenance page layout and admin controls are unchanged.

Enabled At retains the existing date/12-hour format and internal Asia/Manila
conversion, without a visible location suffix. No stored timestamps, maintenance
settings, or database schemas were changed by this update.

## Countdown synchronization correction

Root cause: the display ran only once per second and each three-second state poll
reset its relative sample from an integer server timestamp at response receipt.
Transport delay and scheduling jitter therefore appeared as repeated/skipped
seconds. Device-clock changes also affected the old elapsed-time calculation.

The state response now adds `server_time_ms` (response metadata only, never stored).
The browser measures request/response times using `performance.now()` and derives
a server-clock offset from the round-trip midpoint. Each maintenance event uses
its existing absolute `effective_at` deadline and keeps its initial clock anchor
across polls. Display refreshes run every 200 ms and show
`Math.ceil(remainingMilliseconds / 1000)`. No counter is decremented.
Only whole-second text changes write countdown text into the DOM.

A page singleton prevents duplicate initialization; one guarded poll runs at a
time. Each tab owns one display timer and uses the same server deadline. Ending
maintenance clears that timer and closes the owned modal. New events receive a
new clock anchor. Focus/visibility restoration immediately recalculates and polls.
At zero, the client rechecks current state (with bounded retries), then uses the
existing event-validated logout. Network failure alone never forces logout.
Server request restrictions remain independent of browser timers.

Background tabs can still be throttled by the browser; they catch up to the actual
deadline rather than replaying missed ticks. Clock-offset measurement assumes
roughly symmetric transport delay, as with standard midpoint synchronization.
Older endpoints without the additive millisecond field use their existing
second-resolution timestamp until the endpoint update is deployed.
